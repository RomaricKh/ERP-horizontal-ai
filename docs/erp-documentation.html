🌐 System Overview

ERP-Horizontal-AI is a multi-tenant, multi-business Enterprise Resource Planning web application built entirely without a PHP framework. It targets small-to-medium businesses and provides a comprehensive suite of modules covering the full business lifecycle — from purchasing raw materials to invoicing customers, managing employees, tracking assets, and distributing profits to partners.

The system features 63 database tables, allocation-based settlement for payments and collections, system-typed classifications with module gating, accrual-basis profit calculation with permanent distribution records, PDF generation for invoices and purchase orders, and email-based password reset via SMTP.

Settlement Architecture

Payments and collections use an allocation-based system. A single payment or collection slip can cover multiple documents. The allocation detail rows track exactly which documents are covered and for how much.

Payment/Collection Slip
→
Allocation Rows
→
Document Settlement
Design: Settlement status is determined by SUM(allocations) vs document total — never by payee balance. FIFO auto-allocation distributes amounts across unpaid documents oldest-first by default. Manual override allows picking specific documents and amounts.

System Types Pattern

All classification tables follow a unified pattern for immutable system-defined types with module visibility gating:

Applied to: item_types, payee_types, expense_categories, asset_categories, service_categories.

Modal Architecture

Modals use the openModal() system. Each modal has:

  • HTML template — starts at <div class="modal-dialog">, no outer wrapper
  • JS controller — exports mount({ modalRoot, data }) and unmount()
  • Event bus — dispatches custom DOM events (e.g. module.updated) to notify parent pages
  • Scope — MODAL_SCOPE.PAGE or MODAL_SCOPE.GLOBAL

💳 Settlement & Payments

The settlement system uses an allocation-based approach where payment and collection slips are headers, and allocation rows are the detail showing which documents are covered.

How It Works

Collection Slip (header: amount, date, account, customer) └── collection_allocations (detail rows) ├── SALES_INVOICE #101 → $500 ├── SALES_INVOICE #102 → $300 └── SALES_INVOICE #103 → $200 (total = $1000 slip amount) Payment Slip (header: amount, date, account, supplier) └── payment_allocations (detail rows) ├── PURCHASE_ORDER #201 → $800 ├── EXPENSE #15 → $150 └── SALARY #7 → $50 (total = $1000 slip amount)

FIFO Auto-Allocation

User enters slip amount
→
System finds unpaid documents (oldest first)
→
Auto-distributes amount across documents
→
Creates allocation rows

Settlement Status Rules

DocumentConditionResult
Sales InvoiceSUM(collection_allocations) ≥ invoice totalStatus → PAID
Purchase OrderSUM(payment_allocations) ≥ PO totalStatus → CLOSED
ExpenseSUM(payment_allocations) ≥ expense amountMarked as settled
SalarySUM(payment_allocations) ≥ net amountMarked as settled
Design Principle: Settlement status is always determined by SUM(allocations) vs document total — never by payee balance. The payee balance field is a convenience display value only and is never used for settlement decisions.

Manual Override

Users can override FIFO auto-allocation by manually selecting specific documents and entering custom amounts per document. This is useful when a customer pays for a specific invoice rather than their oldest debt.

🛡️ Recent Core Enhancements

During the most recent system-wide code reviews, several foundational stability and security improvements were rolled out to elevate the ERP's reliability:

Cross-Business Data Isolation
Strict scoping applied to Reports, Dashboard, and Activities. A Business Owner cannot spoof IDs to view parallel business data.
Strict State Machines
Sales Invoices and Purchase Orders now have rigid state locks, preventing allocations to DRAFT or CANCELLED documents.
Partner Currency Precision
Partner investments gracefully handle Foreign Currency (FC) inputs but strictly calculate Base Currency (BC) for the Balance Sheet without double-counting.
Concurrency API Locks
Financial reporting generators across the frontend now lock the UI, preventing multi-click race conditions and database spam.
Historical Statement Accuracy
Balance Sheets rigorously filter modern AR/AP allocations (Credit Notes, Collections, Payments) that occur after the historical snapshot date.
